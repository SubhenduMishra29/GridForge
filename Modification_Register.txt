======================================================================
GridForge V2 — Modification Register
======================================================================

Purpose
-------
This register is the authoritative tracking document for the GridForge
V2 architecture audit.

The audit is being performed before production implementation changes.

No production code is to be patched merely because an inconsistency
is observed.

For every finding:

Finding
    ↓
Evidence
    ↓
Architectural Decision
    ↓
Required Modification
    ↓
Dependency Impact
    ↓
Implementation Order
    ↓
Verification

No tests are to be generated during this composition/dependency audit
unless explicitly requested after the relevant production architecture
has been locked.


======================================================================
GRIDFORGE V2 ARCHITECTURAL PRINCIPLES
======================================================================

#1  Model-centric architecture.

#2  SLD is a current mandatory first-class UI capability.

#3  Context-sensitive engineering workspace.

#4  Blender-inspired interaction/workspace model.

#5  PySide6 implementation.

#6  Electrical semantics remain GridForge-owned.

#7  Core electrical model is completely independent of UI and Blender.

#8  Direct manipulation should make engineering operations visually
    obvious.

#9  UI never performs authoritative electrical computation.

#10 UI state must not replace authoritative Core state.

#11 Core remains the authoritative electrical/model state.

#12 Application-owned services are explicitly composed.

#13 No canvas component may silently create an application-owned service.

#14 Workspace must support flexible docked/floating/tabbed/split editors.

#15 Blender is an interaction/workspace inspiration only; Blender's
    electrical/model architecture is not imported into GridForge.

#16 GridForge UI must combine:
       Blender-style direct manipulation
       +
       ETAP-style electrical semantics.


======================================================================
CORE INTERACTION RULE
======================================================================

For every new UI feature, tool, command, or interaction:

Intent
    What is the engineer trying to accomplish?

Semantics
    What electrical/model operation does it represent?

Interaction
    What is the most direct way to perform it?

Validation
    What makes the operation valid/invalid?

Preview
    Can the consequence be shown before commit?

Feedback
    Is the result visually obvious?

Model
    Does the authoritative Core model change correctly?

GF-AUD-001
======================================================================

File:
    main.py

Layer:
    Application Bootstrap / Composition Root

Severity:
    P2

Status:
    🔵 APPROVED WITH FOLLOW-UP

Finding:
    main.py performs the application bootstrap sequence:

        QApplication
            ↓
        Core Grid
            ↓
        UI Controller
            ↓
        MainWindow
            ↓
        Qt event loop

    main.py does not directly construct the canvas, RenderSystem,
    RendererRegistry, RendererLoader, tools, interaction system,
    navigation system, or other presentation services.

Architectural decision:
    Keep main.py as the executable application composition root.

    main.py should remain intentionally small and delegate UI
    composition to MainWindow and its designated UI composition layer.

Modification required:
    No immediate modification.

Follow-up:
    During MainWindow/workspace audit verify that MainWindow acts only
    as the delegated UI composition boundary.

Related principles:
    #11 #12 #13

Verification:
    Static dependency audit and application composition inspection.

CURRENT ARCHITECTURAL CONCLUSION
======================================================================

The low-level panel architecture currently forms:

    PanelRegistry
          ↓
    PanelDescriptor
          ↓
    PanelManager
          ↓
    PanelInstance
          ├── PanelBase
          └── PanelState
                  ↓
              PanelArea


This chain is currently considered structurally sound.

Do NOT create a duplicate:

    WorkspacePanelRegistry
    WorkspacePanelManager
    CanvasPanelManager
    EditorPanelManager

merely to accommodate the new workspace concept.

======================================================================

    GridScene
    GraphicsView

    RenderSystem
    Renderer
    RendererRegistry
