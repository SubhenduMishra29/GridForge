## 2. Final answer to the Bus-vs-equipment defect

Bus rendered through a dedicated path in `SLDGraphicsItemFactory.create_node()`: the Bus selection is converted directly to `BusItem` from persisted presentation data.

Ordinary equipment deliberately follows the authoritative read-model path:

`SLDNode.equipment_id → Application.read_network()/read_protection() → ElementReadModel → EquipmentFactory.create_from_read_model() → EquipmentItem`.

Therefore an ordinary equipment node with a missing `equipment_id`, or with an ID absent from the Application read state, cannot be realized. The renderer previously caught that failure and continued, which could present as a blank/missing non-Bus symbol while Bus continued to render.

The repository's authoritative creation path already contains the required architectural correction: `Application._coordinate_pre_commit()` validates the just-created Core identity against the Application read model before creating the persistent SLD node. The SLD node receives an independent `node_id` and the canonical Core `equipment_id`, while the engineer's `presentation_x/presentation_y` values are preserved. The existing event/projection path then refreshes the canvas.

Batch 26 therefore did **not** introduce a parallel renderer or fabricate read models. It hardened the existing renderer diagnostic boundary and added regression coverage proving the intended non-Bus realization contract.

## 4. Identity invariant

Static source inspection confirms:

- Core equipment identity is authoritative.
- `Application._coordinate_pre_commit()` reads the newly created element from the Application read model before creating the SLD node.
- `SLDNode.equipment_id` is populated from that canonical identity.
- `SLDNode.node_id` is independently generated by `Application._new_sld_node_id()`.
- `SLDCanvasProjection` copies both identities without remapping them.
- `SLDGraphicsItemFactory` uses `node.equipment_id` to resolve the Application read model.
- No graphics-layer fabrication of missing `ElementReadModel` objects exists for ordinary equipment.

## 5. Synchronization boundary

The persistent presentation authority is `SLDDocument.model` / `SLDModel`.

`SLDProjectionManager` and `SLDReadSynchronizer` remain read/projection infrastructure. `SLDReadSynchronizer` explicitly documents that persistent SLD mutation is not its responsibility.

The canvas chain consumes:

`SLDDocument/SLDModel → SLDCanvasProjection → SLDCanvasSnapshot → SLDCanvasRenderSystem`.

`CanvasPlugin.synchronize_sld()` uses the same `SLDCanvasProjection` and `SLDCanvasRenderSystem` instances owned by `CanvasComposition`. No second active renderer or second persistent SLD model was introduced.

## 6. Renderer diagnostics

Batch 26 preserves the existing diagnostic mechanism and strengthens it with explicit node-realization failure codes:

- `MISSING_EQUIPMENT_ID`
- `EQUIPMENT_READ_MODEL_NOT_FOUND`
- `PRESENTATION_REALIZATION_FAILED`

Each `RenderDiagnostic` retains:

- node ID;
- equipment ID;
- semantic/equipment type;
- symbol ID;
- requested representation;
- category;
- exact exception/message;
- failure code where applicable.

A failed node is not added to the scene and no fake equipment/read model is created.
